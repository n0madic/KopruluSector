# P03: Bullets, terrain scrolling cache, Flingy movement, profiles, cheats and image effect callbacks

This package spans the tail of `cbullet.cpp`, the objects that sort between it and `cflingy.cpp`, `cflingy.cpp` itself, and the objects up to `cimage.cpp`. It falls into seven groups.

1. **Bullet pool persistence and state dispatch** (`0x40a210`–`0x40a9f0`). The pool has 100 records × `0x70` bytes at `0x53db90`. The allocated count is `0x53db8c`, the active list head/tail `0x540750/0x540754` and the free list head/tail `0x540758/0x54075c`. Save/load packs each record as a WORD index plus its raw bytes. The update loop and the state machine are covered by [projectiles](../native-projectiles.md).
2. **Terrain ring-buffer renderer and screen scrolling** (`0x40aa90`–`0x40b870`). The game screen's terrain lives in a 672×448-pixel cache (`0x49800` bytes, stride `0x2a0`), with base pointer `0x543240`. Tiles are addressed toroidally by `((tileY*672 + tileX)*32) mod 0x49800`. A 21×14 megatile window is drawn from the VX4 table `0x543238` and the VR4 pixels `0x543244`. Scrolling redraws only the newly exposed tile columns or rows. It also moves five parallax star-layer offsets, with factors 16/21/26/31/36 from `0x502698..0x5026a8`. The same group refreshes the "remembered" megatile array `0x54323c` for tiles the local player can see.
3. **Generic Flingy movement** (`0x40b940`–`0x40d450`). These functions cover heading/slope math, speed and turn integration, and the prepare/commit split. Prepare computes the next position and flags into scratch globals `0x543280..0x543298` and `0x5432f8..0x5432fb`. Commit then writes them back. Units, Bullets and the independent Flingy all use this machinery. The group also holds the **independent Flingy pool**: exactly **one** `0x4c`-byte record at `0x5432a0`, free list `0x54329c/0x5432ec`, active list `0x5432f0/0x5432f4`. The pool comes with its update, save/load and `flingy.dat` loader.
4. **Player profiles** (`0x40d4f0`–`0x40d830`). These are the `characters\<name>.spc` (single-player) or `.mpc` (multiplayer, byte `0x672664`≠0) files. Each holds a `0x70`-byte record with magic `0x112233`.
5. **Single-player cheats** (`0x40d920`–`0x40e030`). Typed text is lowercased and hashed by an IDEA-based 8-byte MAC. The MAC uses a key derived from the C runtime `rand()` after `srand(0x75)`. The hash is compared against 8-byte constants at `0x4eb97c..0x4eba08`, which toggle bits of the cheat word `0x5432fc`. The group also contains the mission-warp parser for the Ophelia cheat and the immediate effects of the money/upgrade cheats.
6. **Region route cuts** (`0x40e120`–`0x40e4e0`). These are the AI defense-anchor route-cut search, with temporary adjacency removal and restoration. They are covered by [region paths](../native-region-paths.md).
7. **Image callbacks** (`0x40e570`–`0x40ed00`). These are the cloak, decloak and warp-in update callbacks and the drawing-method wrappers installed from the tables at `0x503044` (update) and `0x5030d4` (draw). They are covered by [pixel effects](../native-pixel-effects.md) and [pixel blitters](../native-pixel-blitters.md). The group also holds the image allocators for health bars, selection circles and building-placement previews.

## Shared data and tables

**Flingy movement fields** follow the common head of CUnit/CBullet: `+0x10/+0x12` move target, `+0x14` move-target unit, `+0x18/+0x1a` next movement waypoint, `+0x1c/+0x1e` next target waypoint ("facing target"). Further: `+0x20` movement flags, `+0x21` current heading, `+0x22` turn radius (signed byte in the turn step), `+0x23` velocity direction, `+0x24` Flingy ID, `+0x27` movement type (`flingy.dat` "movement control": 0 = flingy.dat physics, 1 = partially mobile, 2 = IScript-driven). Then `+0x28/+0x2a` pixel position, `+0x2c/+0x30` fixed-point position (×256), `+0x34` top speed, `+0x38` current speed, `+0x3c` committed/next speed, `+0x40/+0x44` velocity vector, `+0x48` acceleration (WORD), `+0x4a` velocity direction being prepared, and `+0x4b` desired velocity direction. Movement-flag bits used here: `0x01` heading/waypoint update pending, `0x02` moving (walking), `0x04` braking toward a computed stop point, `0x08` suppress walking-animation changes. Bits `0x10/0x20/0x40` take part in the deceleration rule of `0x40d260`. BWAPI calls them Moving, Lifted and BrakeOnPathStep; those names are reference labels only.

**Direction table** `0x5026b0`: 256 entries of 8 bytes (signed DWORD x, y), unit vectors scaled by 256. Heading 0 points up, 64 right, 128 down, 192 left. Velocity is always `(table[dir].x * speed) >> 8`, using a low-32-bit product and an arithmetic shift. The recovered values are in [projectiles](../native-projectiles.md) static evidence.

**Tangent table** `0x502eb0`: 64 unsigned DWORDs, searched by `0x40b940`:
`7, 13, 19, 26, 32, 38, 45, 51, 58, 65, 71, 78, 85, 92, 99, 107, 114, 122, 129, 137, 146, 154, 163, 172, 181, 190, 200, 211, 221, 233, 244, 256, 269, 283, 297, 312, 329, 346, 364, 384, 405, 428, 452, 479, 509, 542, 578, 619, 664, 716, 775, 844, 926, 1023, 1141, 1287, 1476, 1726, 2076, 2600, 3471, 5211, 10429, 0xffffffff`.

## Entries

### 0x0040a210 `LoadBulletsV3` — read the Bullet pool from a save (format version ≥ 3)
- Module: cbullet.cpp · Relevance: simulation
- Status: specified
- Signature: `__fastcall`, ECX = `FILE*`; returns 1 on success, 0 on failure.
- Behavior: Reads a WORD `count` with `0x4cc460` (one `fread` element of 2 bytes). A read failure returns 0. If `count` is 0, it returns 1 at once. Otherwise it allocates `count*0x72` bytes with Storm `SMemAlloc` (tag `"CBullet.cpp"`, line `0x558`, flags 8). It then reads that many bytes through the compressed-chunk reader `0x413ae0`(ECX=buffer, EDX=size, stack FILE). On failure it frees the buffer and returns 0. For each record in order, the leading WORD is a pool index `i` (not bounds-checked), and the following `0x70` bytes are copied verbatim over pool record `0x53db90 + i*0x70`. The no-op hook `0x4178d0` runs after each copy. Finally it frees the buffer and returns 1. Pointer fields stay in their saved index form; the caller `0x40a1c0` fixes them afterwards.
- Globals/fields: Bullet pool `0x53db90` (100 × `0x70`).
- Callers/callees: called by `0x40a1c0` (load entry; it first zeroes the whole `0x2bc0`-byte pool, chooses this function when the save version in EDX is ≥ 3, then runs `0x409bb0`(ECX=0, index→pointer) and `0x40a400`).
- Prior evidence: none.

### 0x0040a400 `RebuildBulletListsAfterLoad` — rebuild free/active Bullet lists from loaded records
- Module: cbullet.cpp · Relevance: simulation
- Status: specified
- Signature: no arguments.
- Behavior: A record is live when its sprite pointer `+0x0c` is nonzero.
  1. Free list: find the first record (ascending index) whose sprite is 0. If there is none, free head and tail `0x540758/0x54075c` become 0. Otherwise that record becomes head and tail. Each later free record, in ascending index order, is inserted after the previously inserted one with `0x411900`, which also updates the tail. The head's link fields are not cleared; they are zero from the caller's memset.
  2. Active list: find the first live record. If there is none, active head/tail `0x540750/0x540754` and count `0x53db8c` become 0. Otherwise its prev/next are zeroed, it becomes head and tail, and count = 1. Each later live record has prev/next zeroed and is appended after the previous one; count is incremented each time.
  - Both lists are therefore in **ascending record order**. A fresh pool from `0x40a0e0` has free order 0, 99, 98, …, 1, so allocation order after a load differs from a new game.
- Globals/fields: `0x53db8c`, `0x540750/54`, `0x540758/5c`.
- Callers/callees: `0x40a1c0`; list insert `0x411900`.
- Prior evidence: fresh-pool order in [projectiles](../native-projectiles.md).

### 0x0040a5f0 `UpdateBullets` — per-frame Bullet list step
- Module: cbullet.cpp · Relevance: simulation
- Status: covered
- Signature: no arguments.
- Behavior: As in [projectiles](../native-projectiles.md). For each active Bullet: save `next`; set current Flingy `0x543304` and current Bullet `0x543308` to it; run visibility `0x417e50` and the image step `0x418b20`; dispatch byte `+0x4d` through the jump table at `0x40a6b4` with states 0..6: `0x40a8c0`, `0x409990`, `0x409aa0`, `0x409830`, `0x409a30`, inline, `0x409b00`.
