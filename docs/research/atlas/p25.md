# P25: Lobby messages, game-command execution handlers and command senders

This package covers `0x470460`–`0x474830`: the object `net_chat_cmds.cpp`, the object between it and `net_chrm.cpp`, `net_chrm.cpp`, and the large object between `net_chrm.cpp` and `net_error.cpp`. Its 160 functions form five groups.

1. **Pre-game lobby messages** (`0x470460`–`0x471a40` except `0x471800` and `0x471860`, 36 functions). They build, flush and handle the messages `0x3c`–`0x48` and `0x5b` that the multiplayer chat room exchanges through the turn stream before a game starts: join requests, slot updates, race, force and slot-type changes, the countdown and the start-information message. All are `excluded`, except the lobby-state setter `0x470910`, which single-player game creation also calls (through `0x476600`).
2. **Chat-room protocol** (`0x471800`, `0x471860`, `0x471a90`–`0x471f80`, `0x473be0`; 13 functions). These handle and send the direct Storm messages `'I'`–`'P'` of the network chat room: game information for joiners, force names, chat and whisper text, and rejection. All are `excluded`.
3. **Game-command execution** (`0x472040`–`0x473bc0`, 60 functions, including helpers). These are the per-command handlers that the turn executor `0x475d30` (package P26) calls for every command in the turn stream. Single player sends every player action through the same stream, so this group is fully in scope.
4. **Command senders** (`0x473c70`–`0x474560`, 46 functions). They build command records and queue them with `QueueCommand` `0x476c80`. They are called by console buttons, hotkeys, the minimap, the options and save/load dialogs, and the selection code. All are in scope.
5. **Local IDs and Storm transport wrappers** (`0x474580`–`0x474830`, 5 functions). These reset the local player IDs and wrap `SNetReceiveMessage`, `SNetReceiveTurns`, `SNetSendMessage` and `SNetSendTurn` with the shared fatal-network-error path. Single player runs on a local Storm provider, so the turn wrappers run every turn.

## Shared state

**Command context.** While `0x475d30` executes a player's commands, it sets three DWORDs: `0x508d44` = the issuing player's slot (owner checks and requirement gates use it), `0x508d48` = the issuing player's selection/name index (row of the selection table and of the player table name), and `0x508d4c` = the issuing Storm ID. Afterwards it restores them from the local values `0x508d50` (local slot), `0x508d54` (local selection/name index) and `0x508d58` (local Storm ID). The map `Storm ID → slot` is `0x672878[8]`, and `Storm ID → selection index` is `0x672898[8]`.

**Per-player selections.** `0x6a5ef0 + index·0x30`: 12 unit pointers per selection index, null-terminated. `0x49cb10` resets the cursor `0x6a60a0` and returns the first live selected unit of `0x508d48`; `0x49cb20` returns the next. While advancing, both drop dead units (and call `0x472100`). The handlers below say "for each selected unit" for this iteration and "exactly one selected" for `first ≠ 0` and `next = 0`.

**Last-sent selection mirror.** `0x67261c[12]` holds the unit pointers that the local client last announced with select commands, null-terminated. Every reader stops at the first null. `0x67264c` (BYTE) is the control group last recalled for double-tap detection (`0xff` = none), and `0x672650` holds its `GetTickCount` time.

**Failure feedback is compiled out.** When a requirement gate fails, many handlers read the error code `0x6be654` (`0x4b38a0`) and dispatch through a 25-entry jump table: codes 1, 4, 8 and 25 go to one target, 2 and 23 to another, and all other codes return. Both targets call `0x4be950`(ECX = `0x508d48`, EDX = 0), which is a single `ret`. `0x472210` is the out-of-line copy of the same switch. A failed gate therefore has no side effect. A remake must not add error sounds or messages here.

**Requirement gates** (covered elsewhere): `CanIssueOrder` `0x407bb0`(CX = order, EDX = player, [unit]), `CanUseTech` `0x407f90`(CX = tech, EDX, [unit]), `CanResearchTech` `0x407dc0`, `CanUpgrade` `0x408140`, and the unit-type gate `0x4b32a0`(CX = unit type, EDX = player, [unit]), which sets `0x6be654` on failure. The handlers pass `0x508d44` as the player.

**Order issue helpers** (covered elsewhere): `IssueCommandOnUnit` `0x42a880`(ECX = unit, [queued, order, target]); `IssueOrder` `0x42a2c0`(ECX, [order]); `IssueOrderAtPoint` `0x42a340`; `QueueOrderAtPoint` `0x429ee0`; `IssueOrderOnUnit` `0x42a380`(ECX, [order, target]); `SetSecondaryOrder` `0x42a1e0`; `SetSecondaryOrderForce` `0x42a180`; `EnqueueUnit` `0x41b4b0`. `0x4a7ed0` refreshes the console. Where a handler passes "queued", the value is `msg[1] ≠ 0`.

**Map bounds.** WORDs `0x543230` and `0x543234` hold the map width and height in pixels. `0x5264b4` and `0x5264b6` hold them in tiles.

## Lobby messages (multiplayer only)

Pending outgoing lobby messages are held in heap buffers (Storm `SMemAlloc`) and flushed into the turn stream by `0x470460`: `0x6725d8` `0x3c` start (1 byte), `0x6725dc` `0x3d` download status (2), `0x672598[8]` `0x3e` slot update per slot (6), `0x6725b8[8]` `0x3f` player net info per slot (8), `0x6725e4` `0x41` race (3), `0x6725e8` `0x42` team (2), `0x6725ec` `0x43` force (2), `0x6725f0` `0x44` slot action (3), `0x6725f4` `0x45` slot swap (3), `0x6725f8` `0x48` start info (13), `0x6725fc` `0x5b` make public (1), `0x6725e0` `0x40` join request (18). Incoming lobby messages are dispatched by `0x476650` (P26) with ECX = message and EDX = sender Storm ID. Lobby state byte `0x672600`: 1 after any game creation (`0x476600`, single player included; also `0x4baf60`), 2 on entering the lobby (`0x474c60`), 3 once a join request has been sent (the host's own request in `0x474c60`, a client's after game info `'J'` in `0x471ae0`), 4 when the join is accepted (the host's local join in `0x470af0`, or a client's first slot update moving 3 to 4; handlers require ≥ 4), 5 countdown, 6–8 start phases, 9 started. `0x672604` is the countdown tick counter. `0x672608[8]` is the start-position assignment per slot (8 = none). `0x672610[12]` holds slot types saved from the map setup records.

**Why excluded.** Lobby messages are flushed only by `0x470460`, whose callers are `PollLobbyNetwork` `0x46f3c0` and the lobby teardown `0x474e60`. The only callers of those two are the chat-room dialog (`0x450d80`, `0x4509d0`, `0x474c60`, all reached from the multiplayer chat room `0x450b30`). Their builders are called only from `uimulti.cpp` (`0x4bae80`–`0x4bb2f0`) and from lobby join/countdown code. Single player sends only the briefing ready message `0x54`, which the dispatcher handles inline. The `'I'`–`'P'` chat-room messages are received only through `0x471860`, whose only caller is the chat-room poll `0x474f00`.

### 0x00470460 `FlushLobbyMessages` — queue all pending lobby messages
- Module: net_chat_cmds.cpp · Relevance: network
- Status: excluded (lobby flush; callers `0x46f3c0`, `0x474e60` are chat-room only)
- Behavior: If lobby state is 7, sets it to 8; otherwise returns when the state is above 6. For each non-null buffer in the order `0x6725d8`, `0x6725dc`, `0x672598[7…0]`, `0x6725b8[7…0]`, `0x6725e4`, `0x6725e8`, `0x6725ec`, `0x6725f0`, `0x6725f4`, `0x6725f8`, `0x6725fc`, `0x6725e0`, it calls `QueueCommand` `0x476c80`(ECX = buffer, EDX = its length from the table above), then `SMemFree` and nulls the pointer.

### 0x004709d0 `OnLobbyStartInfo` — message `0x48`
- Module: net_chat_cmds.cpp · Relevance: network
- Status: excluded (lobby message)

For slots 7…0 it assigns start position `msg[5+slot]` with `0x471a40`(force = 1); a value above 8 aborts with the fatal error `0x474a00`(ECX = network string `0x60` "Error launching game.", EDX = 0, [0, 0, 1]); the final stack argument 1 is the `push 1` already made for `0x471a40`.

### 0x00470a30 `OnLobbyForceChangeRequest` — message `0x43`
- Module: net_chat_cmds.cpp · Relevance: network
- Status: excluded (lobby message)
- Behavior: The host, in state ≥ 4, in a Use Map Settings game (`0x447db0`), with force `msg[1]` in 1…4 and `0x443600` = 0, moves the sender's human slot into that force (`0x443500` for the current force, else `0x4433d0`). ### 0x00470af0 `OnLobbyJoinRequest` — message `0x40`
- Module: net_chat_cmds.cpp · Relevance: network
- Status: excluded (lobby message; local call only from the join path `0x4714b0`)
- Signature: `__fastcall`, ECX = message, EDX = sender Storm ID, stack [local flag].
- Behavior: First sets `0x672601 = 0xff`. Host only (`0x475360`). It rejects (`0x471dd0`, reason byte in DL) when the state is not 4 and the call is not local (reason 4), the version WORD `+0xb` ≠ 5 (7), the spawn byte `+0xd` is nonzero and DWORD `+0xe` ≠ `0x4634e0()` (8), or, when loading a save (`0x6a5e34` ≠ 0), `msg[1]` ≥ 8, `msg[2]` ≥ 8 or DWORD `+3` ≠ `0x499860()` (5). Slot choice: UMS without a save → `0x4435c0`; a save in a team or UMS game → the requested slot `msg[1]`; otherwise `0x4794e0`. It then scans the 8 slot records (7…0): every record whose Storm ID equals the sender is reopened (type 6, start position cleared by `0x4717f0`) **and becomes the chosen slot**, so a re-joining player gets the lowest slot it already held. The chosen slot must be < 8 and open (type 6), and with a save `0x471a40`(slot, `msg[2]`, force 0) must succeed; otherwise reason 2. It fills the slot (slot number, Storm ID, type 2; with a save, race `0x5264a0[msg[1]]`), adds the player (`0x477e30`), calls `0x4793b0` and `0x451790`, and stores the player info `0x478120`(flags = WORD `+7` & `0xff03`, plus `0x100` when `+0xd` ≠ 0; WORDs `+9`, `+0xb`). A remote request then sends slot updates for all 8 slots, player info for 7…0 and `'I'` (`0x471f60`); a local one sets state 4 instead. Finally it calls `0x4409b0`/`0x440bd0` when `0x672960` ≠ 0, and `0x476ef0`(`0x479550()`).
