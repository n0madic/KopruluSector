# P25: Lobby messages, game-command execution handlers and command senders

This package covers `0x470460`–`0x474830`: the object `net_chat_cmds.cpp`, the object between it and `net_chrm.cpp`, `net_chrm.cpp`, and the large object between `net_chrm.cpp` and `net_error.cpp`. Its 160 functions form five groups.

1. **Pre-game lobby messages** (`0x470460`–`0x471a40` except `0x471800` and `0x471860`, 36 functions). They build, flush and handle the messages `0x3c`–`0x48` and `0x5b` that the multiplayer chat room exchanges through the turn stream before a game starts: join requests, slot updates, race, force and slot-type changes, the countdown and the start-information message. All are specified: the lobby-state setter `0x470910`, which single-player game creation also calls (through `0x476600`), from the first pass, and the other 35 since the network second pass (2026-11-14).
2. **Chat-room protocol** (`0x471800`, `0x471860`, `0x471a90`–`0x471f80`, `0x473be0`; 13 functions). These handle and send the direct Storm messages `'I'`–`'P'` of the network chat room: game information for joiners, force names, chat and whisper text, rejection and the map-transfer carrier `'O'`. All are specified since the network second pass (2026-11-14), as is `SendNetMessage` `0x474780` of group 5.
3. **Game-command execution** (`0x472040`–`0x473bc0`, 60 functions, including helpers). These are the per-command handlers that the turn executor `0x475d30` (package P26) calls for every command in the turn stream. Single player sends every player action through the same stream, so this group is fully in scope.
4. **Command senders** (`0x473c70`–`0x474560`, 46 functions). They build command records and queue them with `QueueCommand` `0x476c80`. They are called by console buttons, hotkeys, the minimap, the options and save/load dialogs, and the selection code. All are in scope.
5. **Local IDs and Storm transport wrappers** (`0x474580`–`0x474830`, 5 functions). These reset the local player IDs and wrap `SNetReceiveMessage`, `SNetReceiveTurns`, `SNetSendMessage` and `SNetSendTurn` with the shared fatal-network-error path. Single player runs on a local Storm provider, so the turn wrappers run every turn.

## Shared state

**Command context.** While `0x475d30` executes a player's commands, it sets three DWORDs: `0x508d44` = the issuing player's slot (owner checks and requirement gates use it), `0x508d48` = the issuing player's selection/name index (row of the selection table and of the player table name), and `0x508d4c` = the issuing Storm ID. Afterwards it restores them from the local values `0x508d50` (local slot), `0x508d54` (local selection/name index) and `0x508d58` (local Storm ID). The map `Storm ID → slot` is `0x672878[8]`, and `Storm ID → selection index` is `0x672898[8]`.

**Per-player selections.** `0x6a5ef0 + index·0x30`: 12 unit pointers per selection index, null-terminated. `0x49cb10` resets the cursor `0x6a60a0` and returns the first live selected unit of `0x508d48`; `0x49cb20` returns the next. While advancing, both drop dead units (and call `0x472100`). The handlers below say "for each selected unit" for this iteration and "exactly one selected" for `first ≠ 0` and `next = 0`.

**Last-sent selection mirror.** `0x67261c[12]` holds the unit pointers that the local client last announced with select commands, null-terminated. Every reader stops at the first null. `0x67264c` (BYTE) is the control group last recalled for double-tap detection (`0xff` = none), and `0x672650` holds its `GetTickCount` time.

**Failure feedback is compiled out.** When a requirement gate fails, many handlers read the error code `0x6be654` (`0x4b38a0`) and dispatch through a 25-entry jump table: codes 1, 4, 8 and 25 go to one target, 2 and 23 to another, and all other codes return. Both targets call `0x4be950`(ECX = `0x508d48`, EDX = 0), which is a single `ret`. `0x472210` is the out-of-line copy of the same switch. A failed gate therefore has no side effect. A remake must not add error sounds or messages here.

**Requirement gates** (covered elsewhere): `CanIssueOrder` `0x407bb0`(CX = order, EDX = player, [unit]), `CanUseTech` `0x407f90`(CX = tech, EDX, [unit]), `CanResearchTech` `0x407dc0`, `CanUpgrade` `0x408140`, and the unit-type gate `0x4b32a0`(CX = unit type, EDX = player, [unit]), which sets `0x6be654` on failure. The handlers pass `0x508d44` as the player.

**Order issue helpers** (covered elsewhere): `IssueCommandOnUnit` `0x42a880`(ECX = unit, [queued, order, target]); `IssueOrder` `0x42a2c0`(ECX, [order]); `IssueOrderAtPoint` `0x42a340`; `QueueOrderAtPoint` `0x429ee0`; `IssueOrderOnUnit` `0x42a380`(ECX, [order, target]); `SetSecondaryOrder` `0x42a1e0`; `SetSecondaryOrderForce` `0x42a180`; `EnqueueUnit` `0x41b4b0`. `0x4a7ed0` refreshes the console. Where a handler passes "queued", the value is `msg[1] ≠ 0`.

**Map bounds.** WORDs `0x543230` and `0x543234` hold the map width and height in pixels. `0x5264b4` and `0x5264b6` hold them in tiles.

## Lobby messages (multiplayer only)

Pending outgoing lobby messages are held in heap buffers (Storm `SMemAlloc`) and flushed into the turn stream by `0x470460`: `0x6725d8` `0x3c` start (1 byte), `0x6725dc` `0x3d` download status (2), `0x672598[8]` `0x3e` slot update per slot (6), `0x6725b8[8]` `0x3f` player net info per slot (8), `0x6725e4` `0x41` race (3), `0x6725e8` `0x42` team (2), `0x6725ec` `0x43` force (2), `0x6725f0` `0x44` slot action (3), `0x6725f4` `0x45` slot swap (3), `0x6725f8` `0x48` start info (13), `0x6725fc` `0x5b` make public (1), `0x6725e0` `0x40` join request (18). Incoming lobby messages are dispatched by `0x476650` (P26) with ECX = message and EDX = sender Storm ID. Lobby state byte `0x672600`: 1 after any game creation (`0x476600`, single player included; also `0x4baf60`), 2 on entering the lobby (`0x474c60`), 3 once a join request has been sent (the host's own request in `0x474c60`, a client's after game info `'J'` in `0x471ae0`), 4 when the join is accepted (the host's local join in `0x470af0`, or a client's first slot update moving 3 to 4; handlers require ≥ 4), 5 countdown, 6–8 start phases, 9 started. `0x672604` is the countdown tick counter. `0x672608[8]` is, per lobby slot, the record index that slot takes in a saved game being resumed (8 = none; a new game leaves every entry at 8, see `0x471a40`). `0x672610[12]` holds slot types saved from the map setup records.

**Why they were excluded.** Lobby messages are flushed only by `0x470460`, whose callers are `PollLobbyNetwork` `0x46f3c0` and the lobby teardown `0x474e60`. The only callers of those two are the chat-room dialog (`0x450d80`, `0x4509d0`, `0x474c60`, all reached from the multiplayer chat room `0x450b30`). Their builders are called only from `uimulti.cpp` (`0x4bae80`–`0x4bb2f0`) and from lobby join/countdown code. Single player sends only the briefing ready message `0x54`, which the dispatcher handles inline. The `'I'`–`'P'` chat-room messages are received only through `0x471860`, whose only caller is the chat-room poll `0x474f00`. No offline path reaches any of them; the lobby messages, the chat-room messages and `SendNetMessage` `0x474780` are specified since the network second pass (2026-11-14) for the network design.

### 0x00470460 `FlushLobbyMessages` — queue all pending lobby messages into the turn
- Module: net_chat_cmds.cpp · Relevance: network
- Status: specified
- Signature: no arguments, no return value.
- Behavior:
  1. Lobby state `0x672600` = 7 → state = 8 and flush. Otherwise a state above 6 (unsigned) returns at once: nothing is sent in states 8 and 9.
  2. For each pending buffer in this fixed order: `QueueTurnCommand` `0x476c80`(buffer, length), then `SMemFree`(buffer, "net_chat_cmds.cpp", line, 0) and the pointer = 0. Order and lengths: `0x6725d8` (`0x3c`, 1), `0x6725dc` (`0x3d`, 2), `0x672598[7…0]` (`0x3e`, 6 each), `0x6725b8[7…0]` (`0x3f`, 8 each), `0x6725e4` (`0x41`, 3), `0x6725e8` (`0x42`, 2), `0x6725ec` (`0x43`, 2), `0x6725f0` (`0x44`, 3), `0x6725f4` (`0x45`, 3), `0x6725f8` (`0x48`, 13), `0x6725fc` (`0x5b`, 1), `0x6725e0` (`0x40`, 18). Free lines `0xad`…`0xbe`.
- Each message type has one buffer (the `0x3e` slot updates one per lobby slot, the `0x3f` player records one per Storm ID), and the builders overwrite a buffer that has not been flushed yet. Two requests of the same kind within one 250 ms poll therefore coalesce into the later one. The host's own `0x48` is built in state 7 and leaves in this flush, which moves the host to state 8 like the clients.
- Callers/callees: `PollLobbyNetwork` `0x46f3c0` (`0x46f426`, once per executed lobby turn) and `AbortNetworkGame` `0x474e60` (`0x474e82`).
- Second pass (2026-11-14): excluded while the remake had no network play; specified for the network design.

### 0x00470930 `LobbyCountdownTick` — the turn counter that starts the game
- Module: net_chat_cmds.cpp · Relevance: network
- Status: specified
- Signature: no arguments, no return value.
- Behavior: c = `0x672604`; c = 0 → return. Otherwise c −= 1 and stored. L = `0x672660` (turns in transit).
  1. c = 2·L + 4 → `LockLobbySlotsThunk` `0x451770` and state `0x672600` = 6.
  2. c = L + 2 → on the host (`IsGlueGameActive` `0x475360`) state = 7 and `BuildStartInfoMessage` `0x471410`; on a client state = 8.
  3. Finally state = 9 when c = 0, else the state as left by steps 1–2.
- `OnLobbyStartGame` `0x4712d0` sets c = max(2·L + 4, 24), which is 24 for every L ≤ 10 (L is at most 8). Because the counter moves once per executed lobby turn and every seat executes the same turns, all seats lock the slots, receive `0x48` and reach state 9 at the same turn. The host's `0x48` is queued at c = L + 2; with L turns in transit it is executed on every seat before c reaches 0, while the seats are still in state 8, which its handler requires.
- Callers/callees: only `PollLobbyNetwork` `0x46f3c0`.
- Second pass (2026-11-14): excluded while the remake had no network play; specified for the network design.

### 0x00470af0 `OnLobbyJoinRequest` — message `0x40`: the host assigns a slot
