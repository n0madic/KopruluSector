# V01: Verification of disputed atlas claims

This pass resolves nine disputed or decompiler-sensitive claims from the StarCraft 1.17.0.1 atlas against the capstone disassembly of the exact image (`StarCraft.exe`, SHA-256 `94dea44898a3934cdfae2a8149c0044db8ad1af4b4bc54306cdca3b1612d6ed0`, base `0x400000`). Disassembly is authoritative; Ghidra decompilation is not. Every verdict below cites the instruction addresses and branches it rests on. No decompiled code is reproduced.

Enumeration of writers/readers was done by disassembling every atlas function and filtering memory operands by displacement (scripts kept in the session scratchpad); results are stated as instruction addresses.

---

## Item 1 — CUnit status bits `0x20000`, `0x8000`, `0x2`, and flag `0x40` (image versus sprite)

### Status bit `0x20000` (word at CUnit+0xdc, bit 17)

**Question.** Is `0x20000` "IsBuilding" (BWAPI/GPTP label, used by `native-combat-ai.md`) or a can-move/mobility bit (P11)?

**Verdict.** Neither label is the definition, and the BWAPI "IsBuilding" name is wrong. The bit is *initialized from units.dat prototype flag `0x08000000`* and thereafter tracks a unit's current mobility/engagement: it is cleared while a unit is immobilized (merging into an Archon, garrisoned in a grounded building) and recomputed/restored on the reverse transitions. P11's "can-move/mobility" reading matches the writes; the GPTP/BWAPI "IsBuilding" label is a misnomer (buildings generally lack it, and a *lifted* building gains it).

**Evidence — every dedicated writer** (no other instruction sets/clears bit 17; confirmed by a full-image operand scan of `[reg+0xdc]`/`[reg+0xde]`, including 16-bit forms):

- `0x4249e0` @`0x4249f9` — bit-copy `status.0x20000 := units.dat_flags[type] & 0x08000000` (`shr eax,0xa` at `0x4249eb` maps DAT bit 27→17; table `0x521660`, runtime-loaded). Sole caller `0x437320` = transport/bunker **unload restore**. This is the canonical value source and matches `native-transport.md:42` / `native-bunker.md:74`.
- `0x425a70` @`0x425b8d`–`0x425bb3` — unit **creation** initializer; same copy `status.0x20000 := DAT & 0x08000000` (`shr ecx,0xa` at `0x425b94`). (It builds the whole status word: `0x2←DAT 0x2` at `0x425b4c`, `0x4←DAT 0x4` at `0x425b64`, `0x10000←DAT 0x10000000`, `0x20000←DAT 0x08000000`.)
- `0x435f00` @`0x435f6f`/`0x435f78` and `0x437010` @`0x437037`/`0x43703e` — building **liftoff**. Both clear `0x2` (`and …,0xfffffffd`), set `0x10000` (`or …,0x10000`), set InAir `0x4`, and *recompute* `status.0x20000 := NOT(DAT & 0x10)` (`shl eax,0xd; not`). A non-subunit flying building therefore **gains** `0x20000` on liftoff — direct evidence that the bit means "currently mobile," not "is a building." `0x435f00` is gated on `test byte [esi+0xdc],2` + DAT flying-building `0x20`; `0x437010`'s caller `0x46a210` also sets InAir.
- `0x42f9e0` @`0x42f9f6` — `or …,0x20000`: order 106 (Archon/Dark Archon summon **completion**), state `+0x4e` = 1 when animation signal `+0x4f & 4` arrives; the new Archon becomes mobile and receives its default order. (F03 correction: this is not a meld cancel or restore path.)
- `0x42f830` @`0x42f9a8` and `0x42fa70` @`0x42fc00` — `and …,0xfffdffff`: Archon (`+0x4d==0x69`) and Dark-Archon (`+0x4d==0xb7`) meld **complete**; clear `0x20000` on the merge-done path (dist ≤ 2 / ≤ 0x14).
- `0x437c70` @`0x437d26` — grounded-building/**bunker cargo load**: when the transport is a grounded building (`test byte [edi+0xdc],2` at `0x437d0d`) it clears `0x20000` and sets InBuilding `0x20`. Confirms `native-bunker.md:42`.
- `0x425710` @`0x425783` — `mov dword [esi+0xdc],0`: zeroes the whole status word at pool slot init/free.

**Representative readers:** `0x431a46` (combat-AI: produces 3 when set — the behavior `native-combat-ai.md` describes is correct, only the *name* is wrong), `0x432150` (excludes the unit from nonworker-life contribution), `0x432ac0` @`0x432af6` (Ensnare eligibility; F03 correction: `0x432950` is the EMP energy callback, which tests `0x40000000`), `0x481760` (air-density entry; `native-unit-creation.md:48/167`), `0x4aebc0`,`0x4b0f10`,`0x4b1380` (trigger move/unit-action gates, `native-trigger-move-links.md`), `0x42d2a0`.

**Required corrections.**
- `native-combat-ai.md` (branch at `0x431a46`, line ~35/49): replace the `# IsBuilding` label for `0x20000`. Keep the behavioral statement (sets 3). Name it the units.dat `0x08000000` ("Battle Reactions"/Teippi "Reacts") status bit, a mobility/engagement flag, not "IsBuilding."
- Atlas (`p11`-owned entries for `0x4249e0`, `0x425a70`, `0x435f00`, `0x437010`, `0x42f830`/`0x42f9e0`/`0x42fa70`, `0x437c70`): record that `0x20000` is seeded from units.dat `0x08000000` at creation/unload, recomputed to `NOT(DAT 0x10)` on liftoff, and cleared during Archon meld and grounded-building load. P11's semantics stand; drop any "IsBuilding" equivalence.

### Status bit `0x8000` (bit 15) — CanNotAttack / under Disruption Web

**Verdict.** `0x8000` = "may not use ordinary weapons" (Disruption-Web suppression), not a mobility/building bit. **Writers (only two, both ground-only, `test al,4` gate):** `0x43a880` @`0x43a892`,`0x43a8b0`,`0x43a8cc` sets it on every ground unit under a Disruption Web and propagates to the subunit/cargo; `0x438cd0` @`0x438cf4`,`0x438d1c`,`0x438d35` clears stale markers at the start of each Web step (unit id `0x69`=Disruption Web; `native-bw-casts.md:51/55`). **Readers:** `0x408f00` (rejects ordinary weapon spawn, `native-projectiles.md:72`), `0x431e93`, `0x41c81c`, `0x4aaaa0`, `0x4af270`, and the rank-0 branch in combat-AI (`native-combat-ai.md:42` "CanNotAttack / Web"). These agree; no correction needed beyond keeping the name "CanNotAttack/Web," never "building."

### Status bit `0x2` (bit 1) — GroundedBuilding

**Verdict.** `0x2` = grounded building. It has **no dedicated bitwise writer** anywhere in the image (confirmed scan: no `or …,2`/`and …,0xfffffffd` on `[reg+0xdc]`). It is written only as part of whole-dword status computations: set at **creation** from DAT bit `0x2` (`0x425a70` @`0x425b4c`), set on **landing** `0x436fc0` @`0x436fcb` (`and …,0xfffcffff; or eax,2`), and cleared on **liftoff** `0x435f00`/`0x437010` (`and …,0xfffffffd`). Readers are numerous (`test byte [reg+0xdc],2`). Matches `native-combat-ai.md:238` ("grounded-building status bit 2").

### Flag `0x40`: CImage `+0x0c` hidden versus CSprite `+0x0e` burrowed

**Verdict (corrected in [F03](f03-final-fixes.md)).** The flags word that the routines below test is the **image** flags word at CImage `+0x0c`, not a sprite field: `0x415a80` loads ESI = sprite `+0x20` (the image list) and tests `[image+0x0c] & 0x40` per image at `0x415ab4` (set → that image is not blitted). Image flag `0x40` = hidden. It is **set** by `0x40f890` @`0x40f89e` (`or word [image+0xc],0x40`, used by `HideCarriedItemOverlay` `0x416290` on one image), `0x4101b0` @`0x4102ec` and `0x416210` @`0x416272`, and **cleared** by the show routines with masked clears (`0x40f810`, `0x415540`, `0x415a80`, `0x415b30`, `0x417840`). This matches `native-pixel-effects.md:138`.

The **sprite** flags byte is CSprite `+0x0e` ([P05](p05.md) sprite record): `0x01` selection circle, `0x06` ally-selection count, `0x08` selected/health bar, `0x20` hidden (the unit is in the hidden-unit list `0x665af8`), `0x40` burrowed (set only by `0x43d940` @`0x43d955`, cleared by `0x436cf0` @`0x436d82` and `0x43c880` @`0x43c8bb`), `0x80` IScript no-break section. Sprite flag `0x40` selects the cloak draw methods in `0x417400` (set: methods 2..7 reset to 0; clear: 2, 3, 4 become 5, 6, 7). The two `0x40` flags are unrelated.

## Item 2 — spawn flag `0x5085c8` (`0x463710`/`0x4638a0`)

**Question.** Confirm from asm that the flag is 0 on this install, and state what in the glue loop changes because it is 0 (p19 claimed the PalCs theme is never loaded).

**Verdict.** The flag is computed, not constant. `0x4638a0` (grid.cpp; strings `sgubon`, `%s\%s.ccd/.clh/.gid`) ends with `call 0x463710; neg eax; sbb eax,eax; inc eax; mov [0x5085c8],eax` (`0x463998`–`0x46399d`), i.e. `0x5085c8 := (0x463710()==0) ? 1 : 0`. The static initializer at `0x5085c8` is `1`; `0x4638a0` overwrites it at glue bootstrap (caller `0x465de0`). `0x463710` is a non-constant font.ccd lookup/compare: it returns `1` when the lookup succeeds and the compared bytes match (`0x4d019c` result 0, then `neg/sbb/inc` at `0x463771`–`0x463777`), and `0` on a failed lookup, a too-long record (`ja` at `0x463765`) or a mismatch. The host font.ccd decode ("sgubon") matches, so `0x463710` returns 1 and **`0x5085c8 = 0`** on this install. (Polarity corrected after the P19/P22 reviews; the verdict is unchanged.) `0x4635c0` (`mov eax,[0x5085c8]; ret`) therefore returns 0.

**Consequence (refutes p19).** The theme loaders `0x4584e0`, `0x458550`, `0x4585e0`, `0x458690` each gate on `cmp [theme+0x110],0; je load; call 0x4635c0; test eax,eax; jne skip` (e.g. `0x4584e0` @`0x4584f5`–`0x458505`). The skip flag `+0x110` is set only for PalCs. With `0x4635c0()==0` the `jne skip` is **not** taken, so the PalCs cursor, dialog theme, effect bank and font bank **are loaded (and freed) like every other theme**. p19's "the glue loop never loads, or frees, the PalCs… banks" holds only if the flag were 1 (which requires `0x463710()==0`, i.e. a failed lookup or mismatch, contradicted by the host decode).

**Required corrections.** `p19.md` (line 43 and the exit-free notes near line 386): change "That value is statically 1 and is rewritten to 1 by `0x4638a0`, because `0x463710` always returns 0" to: the value is computed `(0x463710()==0)?1:0`; `0x463710` is a non-constant font.ccd compare that returns 1 (match) on this install, so `0x5085c8 = 0` and PalCs is loaded/freed normally. Remove the "never loaded" conclusion.

## Item 3 — constant-result claims

- **`0x4635c0` "always returns 1" (Save Replay always disabled, p21) — WRONG.** It is `mov eax,[0x5085c8]; ret`; not constant. Per Item 2 the runtime value is 0, so it returns **0**. In the Save-Replay handler `0x4620c0`, the sequence at `0x46211a`–`0x46213d` disables the button only if `[0x66b414]` (replay), `[0x66b410]` (loaded save) or `[0x526524]` is set, **or** if `0x4635c0() != 0`; with the flag 0 (`test eax,eax; je 0x462146`) the spawn check passes and Save Replay is **enabled** for a normal finished game. *Correction:* `p21.md` — Save Replay is not force-disabled by `0x4635c0`; its gating is the replay/save/`0x526524` state plus the (currently-0) spawn flag.
- **`0x4832f0` "always returns 0" (p28) — CORRECT.** Each test is on an *address* (`lea eax,[ecx+0x4e8·ecx+0x67d318]`; `test eax,eax; jne 0x483324` at `0x4832fc`…`0x48331c`), never zero for any index, so control always falls to `xor eax,eax; ret` (`0x483324`); the `mov eax,1` at `0x48331e` is unreachable. Confirmed.
- **`0x489070` "always returns 0" (p30) — return value CORRECT; "goal-found paths dead" OVERSTATED.** Both the early-exit (`0x4890d5`) and the matched-box path converge on the single `xor eax,eax; ret 4` at `0x4890d7`, so it always returns 0. But the matched-box branch (`0x4890b0`–`0x4890d1`) has live side effects: it writes the goal cell at `[edx+ecx*8+0x74]`, stores `0xff`/`1` at `+0x78`/`+0x79`, increments `+0x70` and sets `+0x72=1`. *Correction:* `p30.md` — the goal-recording side effects are **not** dead; only the return value is constant 0.
- **`0x492a90` "always returns 1" (p32) — CORRECT.** The only two `ret` sites (`0x492bc3`, `0x492bf8`) are both preceded by `mov eax,1` (`0x492bbb`, `0x492bf0`); every path exits through one of them. It also has side effects (`mov byte [arg+0x1f],1`, `mov [edx],…`). Confirmed.
- **`0x486bf0` status test "can never reject" (p29) — CORRECT.** At `0x486c10`–`0x486c22`: `eax = status & 0x80000; neg; sbb; neg` yields 0/1, then `inc eax` yields 1/2 (never 0), so the following `je 0x486c3f` is never taken; the `0x80000` test cannot skip the `0x4afb20`/`0x43a070` call. (The *position* compares at `0x486c04`/`0x486c0e` can still skip.) Confirmed.

## Item 4 — `0x42b3b0` MoveState_FixCollision and movement state `0x1e` (30)

**Question.** Which jump-table case leads to the state-30 store at `0x42b6b5`, under what conditions, and is the path pointer valid? (p10: nothing sets state 30; GetFree writes through a null path pointer.)

**Verdict.** **State 30 is unreachable; p10's "nothing sets state 30" is CORRECT.** `0x42b6b5` (`mov byte [esi+0x97],0x1e`) is entry 7 of the jump table `0x42b6dc` (`jmp dword [edx*4+0x42b6dc]` at `0x42b617`, after `dec edx`), so it requires the collision-classification value `edx == 8` at `0x42b60d`. Enumerating every `edx` producer in the function (`mov edx,1/3/4/6`; `and …,0xfffffffe; add edx,6` → 4/6; `setne; add edx,2` → 2/3; `lea edx,[edx*2+5]` → 5/7), the reachable set is `{1..7}`; `edx` is never 8, so index 7 is never selected and `0x42b6b5` is dead. A full-image scan for writes of `[reg+0x97]=0x1e` finds this one instruction only; no other instruction (immediate or register) produces 30 (the register-store transition helpers `0x42ac20`,`0x42bcc0`,`0x42bf10`,`0x42c030`,`0x42c1e0`,`0x42ad30`@`0x42af3a` yield only 0xb,0xc,0x13–0x19,0x1b,0x1d,0x1f,0x20,0x21).

**Path-pointer sub-claim.** The state-30 handler is `0x42bb80` (FSM table `0x42af44`, index 30 → trampoline `0x42aeb9 → call 0x42bb80`; `0x42b3b0` itself is the index-28 handler). At `0x42bbae` it does `mov eax,[edi+0x100]; push [eax+0x14]` with **no null check** on the path pointer `+0x100`, so p10's "reads through a potentially null path pointer" is true *of the code*, but the handler is never dispatched because state 30 is never set. Net effect: dead code; no fault occurs.

**Required corrections.** `p10` (atlas entries `0x42b3b0` and `0x42bb80`): mark the state-30 jump-table case (`0x42b6b5`) and the `0x42bb80` handler as unreachable dead code (`edx==8` never produced); keep the note that `0x42bb80` would dereference a null `+0x100`.

## Item 5 — `0x4caf10` present path when no console overlay mask exists

**Question.** Follow the screen-refresh path (through `0x4cb590` / Storm SDraw) so that frame presentation is fully specified when no overlay mask exists.

**Verdict.** p44 is correct that `0x4caf10` copies nothing to the primary when no overlay mask exists; frame presentation does not depend on that branch. The per-frame present is `0x4c5360`:

1. `0x4cb590` `CanPresent` (@`0x4c536b`): returns 0 and the frame is skipped unless the video state `[0x6d3188]`, draw-enable `[0x66fd24]` and surface handle `[0x66fd28]` are all set **and** the window is not minimized (`call [0x4eb640]` = USER32 `IsIconic` at `0x4cb5ac`; non-zero → return 0). On a pending full refresh (`[0x6d0c4c]`) it marks the whole 640×480 dirty (`0x4cac50(0,0,0x27f,0x1df)`, `0x4c4d70`). It locks the primary via `SDrawLockSurface` (`0x4cb560`).
2. Dirty-rect bookkeeping (`SetRect` via `[0x4eb630]`, `0x4c4800`, `0x4c5490`).
3. `0x4caf10` `RefreshScreen` (@`0x4c5466`): returns immediately when the 8bpp buffer pointer `[0x6d0b8c]` is 0 (`0x4caf1e`); on the black-screen flag `[0x50f0f0]` it full-copies the buffer to the primary via `0x4cb390` (`SBltROP3` SRCCOPY); otherwise it paints the UI layers into the 8bpp buffer and, **only if an overlay mask exists** (`[0x6d0c44]`&&`[0x6d0c48]`), composites the dirty region to the primary through the mask with `0x4cb410` (`STransBltUsingMask`). **Without a mask it blits nothing here and keeps the dirty grid** for the next frame that has a mask.

So when no overlay mask exists, the primary-surface updates come from the mask-independent paths — the black-screen full blit `0x4cb390` and the game viewport drawn directly to the locked primary (`0x6cfbdc` "draw directly to the locked primary"); the retained dirty grid is flushed by `0x4cb410` once the console overlay list (`0x50f0d4`) rebuilds a mask (`0x4cb490`/`0x4cb5f0`: `STransCombineMasks` + `STransSetDirtyArrayInfo`). Presentation is fully specified; p44's claim stands. No correction required.

## Item 6 — remap row 0 (p22) vs blend-table construction (p44)

**Question.** Is the first row (first 256 bytes) of each tileset remap table ever initialized or read; what does it hold; is it visible?

**Verdict.** p22 is correct: for the seven tileset light/fire remap tables (records at `0x508840`: ofire/gfire/bfire/bexpl/trans50/red/green), the loader `0x466810` allocates `(h+1)*256` bytes (`lea esi,[esi+1]; shl esi,8` at `0x466899`) via `SMemAlloc` (Storm Ord. 401, through `0x4d001c`) with its flags argument 0, i.e. **no zero-fill flag** (pushes 0 at `0x46688d`, then line `0xcd`, file and size; F03 correction of the earlier "3-argument" wording), then decodes the PCX into `table+0x100` (`add eax,0x100` at `0x4668b4`, size `h*256`). Row 0 (first 256 bytes) is therefore **left as raw heap contents, not guaranteed zero**. The draw helpers index `table + (level << 8)` (e.g. `0x40eb20` @`0x40eb29`–`0x40eb2c`), so PCX row 0 becomes "level 1" and row 0 of the table is the "level 0" slot. The shipped light/fire/trans overlays drive these tables with non-zero shade levels, so row 0 is effectively never selected and **not visible**; it holds uninitialized bytes if it ever were.

This is distinct from the **blend tables** p44 documents (`0x6cf7b4[3]`, keyed-copy `0x6cfbd0`, single-colour `0x6cfbcc`): those are fully constructed including row 0 (keyed-copy row 0 = identity, making source index 0 transparent). p44's blend construction is correct and its row 0 is meaningful and used.

**Required corrections.** None to p22's factual claim (row 0 uninitialized by the loader) or p44's blend construction. Suggest `p22` note explicitly that the allocation is not zero-filled (so row 0 is indeterminate heap, not zero) and that the valid shade index range is 1..h.

**Unresolved.** I did not exhaustively prove that *no* shipped caller ever passes shade level 0 to these draw helpers; the evidence (decode offset +256, non-zero shade usage) indicates row 0 is not read in practice, but a level-0 call cannot be ruled out purely statically.

## Item 8 — `0x4c3fb0` bevel branch with null clip

**Question.** Can the shipped UI reach the branch that dereferences a null clip?

**Verdict.** No; p42's conclusion is CORRECT. `0x4c3fb0` (DrawBitmapButton) is invoked only for a control that has a bitmap: its dispatcher `0x4c3860` jumps to it only when `[ctrl+0x10] != 0` (`0x4c3863`–`0x4c386a`). At entry it loads the clip arg `eax=[ebp+0xc]`; `test eax,eax; jne 0x4c41c0` (`0x4c3fbf`). The clip==0 fall-through draws the bevel (lines via `0x4c4650`, fills via `0x4ce7d0`, no clip deref) and then **falls into** the shared bitmap-blit tail at `0x4c41c0`, which — because the control always has a bitmap — calls `0x4c3c70` passing the (null) clip (`push eax` at `0x4c41ce`). `0x4c3c70` dereferences the clip at its first data access (`mov esi,[ebp+0xc]; movsx edi,word [esi]` at `0x4c3c78`/`0x4c3c84`), so a clip==0 invocation faults before the bevel can complete.

The shipped dialog paint never passes a null clip. The only indirect call of a control draw procedure (control `+0x2e`, the only load of that field at `0x4c5310`) is `call eax` at `0x4c5313` in `0x4c51c0`, whose clip argument is the address of the stack-local rectangle `[ebp-0x14]` (`lea eax,[ebp-0x14]; push eax` at `0x4c5308`/`0x4c530b`); `0x4c51c0` is called only by the dialog-layer painter `0x4c4d90` (`0x4c4f98`, `0x4c5036`). (Corrected in F03: the earlier citation `0x4c4b28`/`0x4c4b42` lies in `InvalidateControl` `0x4c4ae0` and is a pair of `SetRect` calls, not a draw call.) The clip is always a valid non-null pointer. Hence the clip==0 bevel branch is dead in the shipped UI.

**Required corrections.** None; p42's note ("the bevel path cannot complete … normal painting always passes a clip") is confirmed.
