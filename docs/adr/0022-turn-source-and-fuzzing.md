# ADR 0022: The turn source and fuzzing

Status: accepted (phase T, 2026-11-15). The user approved the design of phase T inline on 2026-11-15, with stage T3 first ([ADR 0021](0021-state-walk-and-saves.md#addition-the-dumps-coverage-stage-t3)). Stage T1, the turn source, and stage T2, the fuzzing ([below](#stage-t2-fuzzing)), are built. Stages and their state: [docs/phase-turns.md](../phase-turns.md).

## Context

Each step of the session (`kp_session_step`) gathered its own commands. They came from the interface's queue and, in a replay, from the record's feed (`FeedReplayCommands` 0x4769b0), with the Storm ID to player map, the frame count, the end and the playback's filter of the live commands kept in the session's own fields. The recorder took the local player's commands from the queue. A network game needs a third source whose frame can be not ready, and a recorder that keeps every seat's commands. The session also had to stop exposing those fields to the flow, the scripts and the tests.

## Decision

1. **One source of turns** (`native/kp_app/kp_turns.{h,c}`, `KpTurns` in `KpSession.turns`). The session asks it for each frame's commands (`kp_turns_frame`) and tells it when they ran (`kp_turns_done`).
2. **Two kinds, an enum and a switch**, not a table of functions: there are two real sources, and concrete comes before generic.
   - `KP_TURNS_LOCAL`: the commands queued for the next step, each a whole buffer of the player it was queued for (`kp_execute_command` runs one command a buffer, as the interface queues them).
   - `KP_TURNS_REPLAY`: the record's commands of the frame, each buffer walked as `ExecuteTurnCommands` 0x475d30 walks it (`kp_record_split`) and played as the player whose record has its Storm ID; then the live commands the playback lets through.
3. **The playback's filter at the submit.** `kp_turns_submit` refuses in a replay what the step used to drop: everything but the keep-alive, restart, pause and resume, the sync, the network's 0x37-0x3b, latency and the replay speed (table 0x47636c). It also refuses, in every source, an empty command and a player past the seats (0..7), which the dispatcher has no use for. A save's queued commands are restored through it too, and a save whose queue holds one it would refuse is refused as "bad commands" before the game changes (code review of 2026-11-15: a save's queue took any byte as its player and an empty command loaded, the game then stopping at the next step).
4. **The frame's status.** `KP_TURNS_READY`, `KP_TURNS_ENDED` once at the frame the record passes the header's frame count (the session opens the victory dialog and pauses the playback, as before; the live commands still come) and `KP_TURNS_NO_MEMORY` (the session fails the game). A network source adds "not ready": the step does not run and the clock keeps no missed steps (a TODO in `kp_turns.h`).
5. **The recorder watches the executed list** (`kp_turns_record`), not the queue. It records each command of a buffer whose player has a Storm ID: in a game played alone the local player, ID 0, which gives the same bytes as before. A network source fills the seats of every player; a viewer is a replay over a growing record.
6. **The session keeps the recorder** (`KpSession.rec`, a recorded game's only) and the recorded header, loads and loss. `pending`, `playing`, `replay_*` and the step's list left the session. The flow and the scripts read `kp_session_playing`, `kp_session_replay_ended` and `kp_session_replay_frames`.
7. **Nothing else changes.** The save (CMDS from the source's queue, REPL from the recorder), the replay file, `KP_SAVE_VERSION` and `KP_REP_SIM_REVISION` stay the same. All in one thread, synchronously from the session's step: the web has no threads and determinism matters.

## Consequences

- The tests that bind the behaviour to the original are unchanged and pass: the 65 replays against the original's playback at every step, every golden scenario, play and idle run recorded and played back (`test_session.replay_*_play_back`), the three records byte for byte (`session_replay_records_as_the_original`), the product scripts.
- `test_session.turns_local_queue_and_recording` and `turns_replay_feed_and_live_commands` test the source without a game: the queue's order, players and limits; the recording's seats and the split of a buffer; the feed's Storm ID map with the player kept for an unknown ID; the filter; the end given once.
- A command a playback does not let through is refused when it is submitted instead of taking a place in the queue until the step. The interface ignores the refusal, as it ignored the drop.

## Stage T2: fuzzing

### Context

Every replay, save and map a player opens is untrusted, and so is every frame of a network game ([replay-network-notes.md](../research/replay-network-notes.md#design-questions-the-original-leaves-open), item 6). The readers are bounds-checked and the game stops itself on a state it cannot hold (`kp_game_fail` under the session's guard), but nothing searched for the inputs those checks miss.

### Decision

1. **Four targets, one entry each** (`tests/c/kp_fuzz.{h,c}`). libFuzzer's drivers (`tests/fuzz/kp_fuzz_main.c`, one executable `fuzz_<target>` a target) and the suites (`test_fuzz`) call the same entries:
   - `rep`: `kp_rep_read`, `kp_session_replay_start` and the turn source's feed of every frame (at most 30,000); a file read is written back and must read again (a property: its failure is a finding);
   - `chk`: `kp_chk_read` with and without the expansion, and `kp_mission_from_chk` when the game's data is present;
   - `save`: the first byte's low bit picks the form. A save file: its KPF's CRC-32s made right, `kp_save_check`, then `kp_save_load` into a recorded session. A native save: edits of the game's own save (below), its hash table made right, then `kp_load` into the game;
   - `commands`: the first byte picks one of three scenarios (workers and buildings, a fight, a computer's spells); then chunks {u8 player | steps << 3, u8 n, n bytes}, whose bytes `kp_record_split` walks into commands of players 0-7, each chunk followed by its steps (at most 8 in all). Since phase N's review each input runs in the scenario's single player game and then in its network game (the game's multiplayer).
   The games start once a process; each input begins from their snapshot (`kp_restore`, the turn source's queue and the game's events emptied).
2. **A save's hash table made right by the harness** (`kp_save_seal`, `kp_game.h`). The table detects damage and authenticates nothing, so anyone can remake it; without that, every mutation stops at the table and the fuzzer never reaches the walk's own checks.
3. **A native save as edits by section.** A native save is 8 MB, past libFuzzer's inputs (1 MB by default). The input is edits {u8 section, u24 offset, u8 n, n bytes} of the game's own save, the section taken modulo the count and the offset modulo its size (`kp_save_sections`, `kp_game.h`: the sections kp_load's dry walk finds). A small section's counts are hit as often as a large one's arrays.
4. **The build:** the CMake option `KP_FUZZ` (clang with libFuzzer, LLVM's: Apple's has none; with `KP_SANITIZE`), `-fsanitize=fuzzer-no-link` on every C and C++ source and `-fsanitize=fuzzer` on the drivers. `tools/fuzz.sh` builds `build/cmake-fuzz` with `KOPRULU_CLANG` (else Homebrew's llvm), makes the seeds and runs each target `KOPRULU_FUZZ_TIME` seconds (default 60). The targets that need the game's data (`save`, `commands`) are skipped without it; with the data, a game of theirs that does not start fails the seeds (`kp_fuzz_seeds` exits 1) instead of passing for a skip.
5. **Seeds** (`kp_fuzz_seeds [--synthetic] DIR`):
   - the synthetic ones are committed in `tests/fuzz/seeds/`: a replay of a made-up header, record and map, a CHK of the sections every version requires (its VCOD zeros: the reader refuses it at that digest, Blizzard's bytes stay out of the repository), and plain orders for the three scenarios;
   - the ones made from the data go to `build/fuzz/seeds/` on each run and are never committed: the CHKs of four campaign missions and three scenarios, the save target's game as a file and as native edits at three points, the replay of a recorded game, commands on each scenario's own units, and an order past orders.dat.
6. **What counts as a finding:** a crash, an ASan or UBSan report, a leak, an input that runs 30 s, or a failed property. libFuzzer writes an input slower than `-report_slow_units` as an artifact too (10 s by default), so `tools/fuzz.sh` sets it to the hang's 30 s: a slow input alone is no finding. A game the game's own checks stop is a refusal: counted by its reason (its numbers masked, a command's id kept) and reported, not a finding. In a network game a refusal is a finding: every seat runs every seat's commands, so it would be one seat stopping the game for all.
7. **The findings kept:** minimized into `tests/fuzz/regress/<target>/`, or `koprulu-private/fuzz/regress/<target>/` when they hold the data's bytes (a save, a mission's CHK, a recorded replay). `test_fuzz` runs the committed seeds and the kept findings through the entries in every build (the host, ASan/UBSan, wasm): `kept_*_inputs`. `data_seeds_run` makes the data's seeds and runs them too: every save the game made loads in both forms, and the three orders past orders.dat are refused and nothing else is (the network game ignores them). `seal_makes_the_hash_table` checks the seal.
8. **CI:** the full mode (`KOPRULU_FULL`) runs `tools/fuzz.sh` after the LLVM sanitizer step, with that clang. The pass is never remembered: each run searches on from the corpus the last one left in `build/fuzz/corpus/`. The step is skipped when the clang links no libFuzzer (the script's exit 3).

### Consequences

- **The first runs found no crash, sanitizer report, leak or hang** (five minutes a target, the corpus kept from shorter runs before: [phase-turns.md](../phase-turns.md#t2-verification)).
- **The refusals the fuzzer reaches are known ones:**
  - the commands no game played alone sends: shared vision 0x0d, alliance 0x0e, 0x1d, 0x38-0x3b, leave game 0x57 and chat 0x5c (`kp_commands.c`'s handler table says why each has no sender offline);
  - a targeted order 0x15 past orders.dat (order 0xff). The original reads its tables past their end (`ExecTargetedOrder` 0x472270, tech `0x51b800[order]`). Koprulu's DAT read gives `KP_NIL` there, and the requirements' range check stops the game.
  A network game ignores such an order instead (phase N's review, [ADR 0026](0026-network-compatible-with-1-17.md#addition-the-review-of-the-network-play)): a refusal there would stop every seat at once, so one modified seat could end everyone's game. The control group 18 of player record 7 (`kp_command_control_group`) is ignored there for the same reason; offline both stay refusals.
- A save made by the game loads after `kp_save_seal` exactly as before: a save sealed again is the same bytes. The seal changes no save format and no `KP_SAVE_VERSION`.
- Running a game on after a fuzzed load was not covered at first: the save target loaded and went back to its snapshot. Since 2026-11-22 the loaded game runs on ([the addition below](#addition-a-loaded-save-runs-on-2026-11-22)).

### Addition: the network's targets (phase N, stage N2)

Phase M added `turns` (the seats' hub, [phase M](../phase-multiplayer.md)). Stage N2 ([phase N](../phase-network.md#n2-kp_snet-and-the-udp-provider-done-2026-11-17)) adds two, in `tests/c/kp_fuzz_net.{h,c}`, with the same entries, drivers, CI step and kept-findings rules as above:

- `udp`: `kp_snp_udp` alone, at 10.0.0.1 among fifteen peers whose datagrams are the input's (either port; a bit of the op makes the length field and the checksum right, so mutations pass Storm's checks), with its clock, the game list walked and looked up, advertisements started and stopped, and datagrams of its own;
- `snet`: `kp_snet` over the provider, with the same datagrams and clock, the pump thread's passes, turns, messages and the other exports, a join among them (its handshake's wait takes the input's datagrams that came during it).

Their properties: every datagram the stack sends is well-formed (its length field and checksum; a game-list datagram at most the list socket's 532 bytes), the events are in range (a present player's event excepted: it carries a player info's id dword whole, as Storm's `0x15023660` does, and StarCraft's `OnPlayerJoined` `0x4778e0` ignores ids from 8 up; the full CI's 60 s found it on 2026-11-22, `tests/fuzz/regress/snet/player-info-id-dword`), what the stack received and handed out is read whole (ASan sees a stale pointer), and its tables stay in their bounds (`KP_SNP_QUEUE`, `KP_SNP_GAMES`, `KP_SNET_RECORDS`). The seeds (`tests/fuzz/seeds/udp/provider`, `snet/host`, `snet/join`) are made by the interpreter itself while the stack plays with a whole Koprulu peer on the in-process LAN, so they hold Koprulu's own traffic and nothing of the original's; `test_fuzz` replays each and checks its digest, and the `snet` seeds must carry at least 20 of the peer's turns.

### Addition: the network game after its start (phase N, 2026-11-21)

The lobby's targets `lobby` and `transfer` (stage N3) stop at the start. `game` (`tests/c/kp_fuzz_game.{h,c}`, [phase N](../phase-network.md#the-remaining-code-items-2026-11-21)) goes on from there: one seat's network game, started once a process (it needs the game's data, as `save` and `commands` do) and back at its snapshot for each input, over a Storm whose turns, messages, failing calls, turns in transit and clock are the input's, with the seat's own commands and chat lines; the frames run through the session's `KP_TURNS_NET` as the product's. Its properties: the seat's sends within the provider's message size, its outgoing turn and turn's list within their bounds, and its game never stopped (a stop is every seat's, as in the `commands` target's network game). Its seeds are synthetic (`tests/fuzz/seeds/game`), and `test_fuzz.game_seeds_reach_their_paths` checks that each reaches what it is for.

### Addition: a loaded save runs on (2026-11-22)

- **The save target runs 8 frames** (`SAVE_LOAD_STEPS`, `kp_fuzz.c`) after `kp_load` takes a native save, then goes back to its snapshot. A stop of the game's own checks in those frames is a refusal, counted as the others. The snapshot's reset also empties the session's record, which a save's queued commands would grow.
- **A seed proves the steps run:** a save made with a select and an order past orders.dat in its command queue (`file-queued-order-past-orders-dat.kpsave`). The load takes it and only the loaded game's frames refuse the order; `test_fuzz.data_seeds_run` wants that one refusal, and fails without the steps.
- **The first minute found a loader defect.** A save whose scalars had a presence byte other than 0 or 1, a scalar the game always holds marked absent (`KP_NIL`), or a value outside 32 bits loaded, and the game's next step computed `KP_NIL - 1` (UBSan, `kp_step.c`). `kp_load` now refuses such scalars: `KpScalarInfo.held` names the globals a game always holds (all but the command player, the second order, the screen's rectangle and the placement's order and type, which a state may lack). The check comes after the hash table's, so a damaged section still reads as damaged; `test_save.loads_refuse_scalars_a_game_cannot_hold`. The input stays in `koprulu-private/fuzz/regress/save/` (it is a game's save).

### Addition: the viewers' protocol (2026-11-27)

`watch` ([the protocol](../formats/watch-udp.md), ADR 0027) interprets its input as a server and a viewer over a link it drops or forges datagrams on: forged DATA (a part, the final flag, a bad CRC, an offset at or past what the viewer holds, a size from the offset), raw datagrams both ways, ticks and polls over the link, the host's record growing (commands, marks, the end), the viewer's take and the mark taken back (a load). Its properties: every REQUEST the viewer sends is well formed; every DATA the server sends is no larger than the REQUEST it answers, well formed, its bytes within the part and their CRC right; the viewer keeps only bytes that follow what it holds and takes nothing past the record's cap (`KP_WATCH_RECORD_MAX`, a replay's largest record: a larger announced size ends the game where it came to). The seeds are synthetic (`tests/fuzz/seeds/watch`); two minutes ran 2.06 million inputs clean.
