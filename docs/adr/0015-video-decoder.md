# ADR 0015: The VP9 decoder for the cinematics, an optional build dependency

Status: accepted (cinematics, 2026-10-31; the user approved it after the C0 measurements). It changes the dependency policy of [ADR 0012](0012-sdl3-runtime.md) item 5 and the line of [ADR 0013](0013-remastered-data-source-and-hd.md) "the runtime gains no dependency" for the builds that ask for the cinematics. The user chose libvpx, the cinematics as Remastered ships them (VP9 as is), the SD and HD2 variants selectable apart from the art, desktops and Android first, the library optional at build time (2026-10-31). Its cinematics packs (`CINE`) and its transcode through FFmpeg and oggenc are replaced by [ADR 0019](0019-install-or-repack-converter-in-c.md) (phase C, 2026-11-11): the movies are read from an install or the repack, the 1.17 SMKs transcoded by `kp_convert` in C.

## Context

The product plays no full-screen movie. `kp_hud.c` skips a campaign's cinematic rows and the main menu's View Intro does nothing. The original played 28 cinematics (`smk\blizzard`, `starintr`, `PreTerran_1..4`, `Terran1..4`, …, `xZerg`; `docs/research/atlas/p28.md`, `PlayCinematic` `0x47ec60`) from Smacker files in `StarCraft.mpq` and `BroodWar.mpq` (610 MB).

The product's only data source is Remastered (ADR 0013). Its storage holds the same 28 as WebM: `SD/smk/*.webm` (VP9 profile 1, 4:4:4 `gbrp`, 320 × 308, 15 fps, Vorbis 22.05 kHz stereo, 198 MB) and `HD2/Smk/*.webm` (VP9 profile 0, 4:2:0, 960 × 540, 15 fps, Vorbis 48 kHz stereo, 329 MB). The SD frames are stored half as wide as they are shown: the content of HD2 (960 × 458 of 960 × 540) is 1.5 × 640 × 308, so an SD frame is shown 640 × 308, a pixel of 2:1.

A palette movie format like KPV1 (portraits, glue movies) cannot carry them: full colour, 2000 to 3600 frames per movie, one soundtrack. The runtime has no video decoder, and ADR 0012 and 0013 say it should not gain one.

## Decision

1. **Decoder: libvpx 1.17.0, VP9 only, as an optional build dependency.**
   - `-DKP_CINEMATICS=ON` fetches the pinned source (`tools/toolchain/fetch.sh vpx`, SHA-256 `1020f184046187baa2985dbde38e0691f49c44088bca7a1842b0236c6081dc0a` of the GitHub tag archive) and links it statically. The default is OFF: no library, no module, no file in the bundle, the behaviour of today. ADR 0012 item 5 and ADR 0013's line hold for the default product.
   - Built without threads (`--disable-multithread --disable-vp8 --disable-vp9-encoder --disable-vp9-highbitdepth`; on arm64 and in C without an assembler or runtime CPU detection, `--disable-runtime-cpu-detect`), its sources listed in a CMake file of ours (`third_party/vpx/kp_vpx.cmake`, C11: libvpx 1.17 uses `static_assert`), its few generated headers kept beside it (`third_party/vpx/generated/`, `regenerate.sh`). On arm64 (macOS, iOS, Android, Linux) with libvpx's NEON intrinsics (`arm64-darwin24-gcc`, `generated/arm64/`; NEON is part of every AArch64 CPU, so it needs no runtime check; dotprod, i8mm and SVE would, and are off). On x86-64 (Windows, Linux, an Intel Mac) with SSE2..AVX2 when NASM 2.14 or later is on the PATH at the configure (`x86_64-darwin24-gcc` with runtime CPU detection, `generated/x86_64/`: libvpx's cpuid picks each function's best at the start; a part of them is in libvpx's `.asm` only, assembled by CMake's `ASM_NASM`; 2026-11-04), else from C. Elsewhere from C (`generic-gnu`, `generated/generic/`). 360 KB of static archive. BSD-3 with the WebM patent grant.
2. **The movies as Remastered ships them.** The converter copies the VP9 packets (`ffmpeg -c:v copy -f ivf`) and the Vorbis stream (`-c:a copy -f ogg`) into a pack of our own (`CINE`, `docs/formats/packs.md`), with a frame table. No second lossy pass, no Matroska parser in C. The audio plays through the SDL3_mixer already built (Ogg Vorbis through stb_vorbis) and also keeps the movie's clock.
3. **The quality is chosen apart from the art.** `generated/video/cinematics-sd.kpd` and `cinematics-hd2.kpd` are independent packs; `tools/product.sh` takes `KOPRULU_CINEMATICS=auto|none|sd|hd2|both` (auto, the default, takes the HD2 pack, else SD's, else none) whatever HD art it stages; the runtime flag `--cinematics auto|sd|hd2|off`.
4. **Targets:** macOS, Windows (mingw cross), Linux, Android, iOS and the web (the last two since 2026-11-04, approved by the user after an inline design).
   - iOS is built as Android is (NEON, the pack in the bundle, read from its file). `--cine-check` on the iOS Simulator: 28 movies, 31,156 frames, 0 failures, each movie up to 3.2 ms a frame on average and 20 ms at the longest, on a Mac busy with builds; a real iPhone was not measured.
   - The web has libvpx from C in wasm, and no file to read at once: the pack lies beside the page, its head preloaded (`tools/web_hd_heads.py`, up to `DATA`, which it refuses anywhere but last), its packets fetched over HTTP Range requests (`KpCineStream`: chunks of 1 MB, one at a time until a range is answered, then 4 from the read on). The sound is fetched whole once the movie's first packets have come and plays from memory. A packet that has not come answers `KP_CINE_READ_WAIT`: `kp_cine_advance` gives `KP_CINE_WAIT`, the run holds the movie's clock (`kp_cine_clock_hold`) and its sound and goes on from the same packet; a press made since its first wait ends a movie that waits, though it has shown nothing (not one from before it: the second finger of the press that ended the movie before). A server that answers a range with the whole file (200) costs that file once: the movie ends and no other is tried (the host clears `KpCineRun.have`). `--cine-check` needs the pack in one piece, so it answers no on the page (the measure below had it preloaded).
   - Measured in Chromium on the Mac, the HD2 pack preloaded: every picture's CRC-32 of its planes the same as NEON's, 0 failures; 0.2 to 5.2 ms a frame on average for each movie, 15 ms at the longest, of the 33.4 ms an HD2 frame has. A phone's browser was not measured.

## Why this decoder

Measured in C0 (libvpx 1.17.0, `generic-gnu`, `-O2`, one thread, the intro `starintr`, 2082 frames):

| | macOS arm64 (M-series) | Galaxy Z Fold7 (arm64, NDK 29) |
|---|---|---|
| SD 320 × 308 4:4:4 | 0.97 ms a frame (max 6.1) | 1.7 ms (max 11; the phone was dozing) |
| HD2 960 × 540 4:2:0 | 3.5 ms (max 9.6) | 5.2 ms (the 255 ms maximum is the dozing CPU) |

An SD frame is due every 66.7 ms (15 fps), an HD2 frame every 33.4 ms (29.97 fps); what counts is the main thread's frame of 16.7 ms at 60 Hz, since the decoder runs in the main thread (the web build has no threads, ADR 0013 R4b). With NEON (10H, after the second review) the product's `--cine-check` over all 28 movies of each pack (mean and longest `kp_cine_advance` a frame: the pack's reads and the decoding; the Mac's release build, the Fold7's debug APK, `RelWithDebInfo`):

| | C (`generic-gnu`) | NEON | the planes |
|---|---|---|---|
| macOS M-series, SD (30,211 frames) | 1.08 ms (max 10.1) | 0.59 ms (max 8.9) | the same CRC-32 |
| macOS M-series, HD2 (31,156 frames) | 2.65 ms (max 13.2) | 1.19 ms (max 12.7) | the same CRC-32 |
| Fold7, SD | 1.04 ms (max 7.8) | 0.56 ms (max 7.7) | the same CRC-32 |
| Fold7, HD2 | 2.78 ms (max 11.7) | 1.04 ms (max 10.4) | the same CRC-32 |

(the intro alone, HD2: 3.56 → 1.96 ms on the Mac, 3.59 → 1.71 ms on the Fold7). NEON's output is libvpx's C output bit for bit (the CRC-32 of every picture's planes of each movie, the same on both machines), so FFmpeg's bit-exactness below still holds (`test_cine.ycc_movie_planes_are_ffmpegs` checks the 4:2:0 planes against FFmpeg's byte for byte, in whichever build runs it). No decoder thread: an HD2 frame takes a sixteenth of the 60 Hz frame on the phone, and the longest call (which frames they are, and how much of them is the pack's reads, was not measured) still fits in it. The output of both movies is **bit-identical** to FFmpeg's decode of the same files (`cmp` of the whole raw output: 615,605,760 bytes of `gbrp` and 1,618,185,600 of `yuv420p`), so the pack's frames can be checked against `ffmpeg` in a test.

Colour as libvpx reports it: the SD movies are `VPX_IMG_FMT_I444`, `cs = VPX_CS_SRGB`, full range, planes in G, B, R order (a direct copy to RGBA); the HD2 movies are `VPX_IMG_FMT_I420`, `cs = unknown`, studio range. C3 chose BT.601 for a picture whose matrix is unspecified (FFmpeg's own guess; BT.709 only when the stream says so): on the test movie the player's frames differ from FFmpeg's `rgba` by 1 at most (`tests/c/test_cine.c`), the chroma copied where FFmpeg filters it. In play the planes go to the GPU and its shader converts them with the same matrix (`kp_gfx_video`, the chroma sampled between its texels); the CPU's conversion stays as the checks' reference (`--cine-check` compares the two).

## Rejected

- **dav1d (AV1) with a transcode.** The source is already VP9: a second lossy pass for no gain, and dav1d builds only with meson, which nothing in the project's build uses.
- **The original SMK files.** The decoder (`kp_smk.c`) is video-only and palette-bound, the files come from the 1.17 archives (610 MB, not Remastered), and ADR 0013 made Remastered the data source. Still rejected for the runtime; the converter turns them into the same pack since 2026-11-09 (below).
- **A VP9 decoder of our own.** A large specification and a bit-exactness check against libvpx for a movie format that libvpx decodes in 3.5 ms.
- **FFmpeg or the platforms' decoders** (VideoToolbox, MediaFoundation, MediaCodec, WebCodecs). A different one on each target, most with no VP9 profile 1, and FFmpeg's size and licence for one codec.
- **An MPEG-1 single-header decoder (pl_mpeg).** Builds anywhere but looks far worse than the source.

## Consequences

- A build with cinematics has one third-party library more; the default build has none. `tools/ci.sh` checks both.
- The packs are large (198 MB SD, 329 MB HD2). `tools/product.sh` stages the best pack converted (`KOPRULU_CINEMATICS=auto`, its default: HD2, else SD, else none; the web's beside the page), so a bundle of converted data carries the movies and, on Android, the APK grows by the pack; `KOPRULU_CINEMATICS=none` leaves them out. The plain CMake build had no player (`KP_CINEMATICS` off) until ADR 0018's stage D6 built the decoders everywhere (below).
- Remastered's subtitle files (`locales/<locale>/Assets/Smk/*.srt`, only the install's own locale downloaded) go into the packs' `SUBS` (schema 2, 2026-11-04) and are drawn over the movies in `ui.kpd`'s TrueType text font (`docs/phase10.md`).
- The libvpx archive pinned is GitHub's tag archive, whose bytes GitHub does not promise to keep: a changed checksum stops the fetch, and the source is then taken from the library's own releases page.

## The 1.17 install's movies (2026-11-09)

A conversion from the 1.17 install had no cinematics ([issue 1](https://github.com/n0madic/KopruluSector/issues/1)). The user approved (2026-11-09) transcoding them at conversion time into the SD pack, the player, libvpx and the pack's format unchanged:

- **Inputs.** The 28 movies are in the archives the profile already needs: `blizzard` in `StarDat.mpq` (its other copies in `StarCraft.mpq` and `BroodWar.mpq` behind it), `starXintr` and the `x*` movies in `BroodWar.mpq`, the others in `StarCraft.mpq` (605 MB). Each is SMK2, 320 × 308 (the briefings `Pre*` 640 × 308), the frame rate field −6666 (50000/3333 fps), one sound track of 22,050 Hz 16-bit stereo Smacker DPCM whose length equals the video's (within 1 ms in all 28). `Resolver.read_expected` checks each effective copy against the size and SHA-256 of the reference install that `defs/campaign/cinematics.json` (`smk`) records; they stay out of `defs/scr/inputs-*.json`, which `--scr` would otherwise try to rebuild as KPV1.
- **Transcode** (`converter/emit/cinematics_smk.py`, `python3 -m converter cinematics --data DIR`). FFmpeg decodes the SMK (its smackvideo frames equal smackw32's for all 28: `docs/research/evidence/smk-decoder-equivalence.json`) and libvpx-vp9 encodes it as Remastered's SD set is: VP9 profile 1, 4:4:4 sRGB (the palette's colours looked up without loss), at the movie's own size (shown 640 × 308 by the player, as Remastered's SD), its exact rate, `-crf 32 -b:v 0 -deadline good -cpu-used 2 -g 128 -threads 1`, straight to IVF. The sound goes through a WAV into `oggenc -q 3` with a stream serial of the movie's name (not FFmpeg's Vorbis encoders: 6.1's starts the sound 46 ms early). No subtitles.
- **Quality and size** (measured on all 28, the M-series Mac). Remastered's SD movies were themselves transcoded from these SMKs; on the ones whose frames match the originals one for one (`blizzard`, `Terran2`, `Zerg3`, `Protoss3`, the briefings; the others have one more frame and drift) our PSNR against the decoded SMK is within 0.6 dB of Remastered's at 5 to 9 % more bytes (`Terran2`: 41.4 against 41.2 dB, 1,632 against 1,525 KB). Over the 28 at `-cpu-used 4`: CRF 24 382 MB of video (the lowest mean 40.2 dB, the worst frame 36.1), CRF 28 273 MB (38.7, 33.8), CRF 32 195 MB (37.0, 31.6); `-cpu-used 2` gains 0.2 to 0.7 dB at the same size. The sound, 13.5 MB at `-q 3`, is Remastered's 13.4.
- **Order.** Every copy is read from the archives and checked first, in the calling thread, and written to a file beside the cache: a copy unlike the reference stops the conversion before any encoding, and the encodings never touch the archives. The caller closes the movies' iterator before the archives close, so a conversion that stops early cancels what is not encoded yet.
- **Time.** libvpx in one thread per movie (the same tools give the same bytes), the movies side by side in a thread pool of one worker per core; 138 s on 14 cores of an M-series Mac (1013 s of CPU), the longest movies (`xProtoss` 137 s, `starXintr` 132 s) setting it. The IVF is cached under `generated/cache/cinematics/` by the movie's SHA-256 and the settings, the Ogg also by its stream serial, so a second conversion encodes nothing.
- **Makefile.** `make convert SC=DIR` ends with `cinematics --optional`: without FFmpeg's `libvpx-vp9` encoder, ffprobe or oggenc the converter warns and writes nothing (`CINE=none` leaves them out); `make cinematics SC=DIR` runs them alone and fails without those tools. A `CINE` given on the command line goes to the converter as `--variant`, which refuses `hd2` for the 1.17 install.
- **One pack per set, Remastered's first.** The 1.17 movies and Remastered's SD set are both `cinematics-sd.kpd`, and Remastered's wins whichever was converted first: `cinematics --scr` writes over a 1.17 pack, and `cinematics --data` keeps a pack there whose source hash is not the 1.17 data set's (`cinematics.remastered_pack`, which reads the container's header alone: `container.header`) and writes nothing; a damaged pack, one of another kind or schema (the player refuses those) or the install's own is converted again. Both packs carry the profile `bw-1.17.0.1`, so the source hash is what tells them apart. `KOPRULU_CINEMATICS=auto` prefers Remastered's HD2 pack anyway.

## Every build has the decoder (ADR 0018, stage D6, 2026-11-11)

[ADR 0018](0018-original-data-at-run-time.md) plays StarCraft: Remastered's WebM as it is: the portraits (VP9) and the glue's overlays (VP8 with an alpha stream) of a Remastered install, and the HD portraits. The decoder stops being optional:

- libvpx is built with its VP8 decoder too (`third_party/vpx/kp_vpx.cmake`: VP8's C, its NEON on arm64, its MMX..SSSE3 and `.asm` on x86-64; the generated headers regenerated, `regenerate.sh`), and nestegg (ISC, the WebM demuxer, a commit pinned by SHA-256: it has no releases) beside it. `tools/toolchain/fetch.sh` fetches both by default.
- `KP_CINEMATICS` is gone: the cinematics' player (`kp_cine.c`) is in every build, `test_cine` always runs. The packs stay optional (`KOPRULU_CINEMATICS`, `--cinematics`), as above.
- The colour conversion is shared (`kp_vpx_rgba`, `kp_vpx_yuv_rgb`, `kp_webm.h`).

## An install's movies played as they are (ADR 0018, stage D7, 2026-11-11)

When the game runs from an install (`--data`), its cinematics are the install's, with no pack: the 1.17 install's (or a repack's) Smacker files, each checked against the reference copy's size and SHA-256 (the profile's compiled `CINM`) and decoded by `kp_smk` (its palette records and its sound, Smacker's DPCM, equal to FFmpeg's decodes); StarCraft: Remastered's WebM, HD2 first, demuxed by nestegg and played by the same VP9 decoder, its Vorbis sound put into Ogg pages for SDL3_mixer, its subtitles read from the install's `.srt` of the player's language, else of the install's text locale, else enUS. A movie is read whole when it begins (`KpCineMovie`). The packs stay for the builds that have no install beside them (the phones and the web) until ADR 0018's stage D8 settles their repack; the converter still makes them.
